Implementation base: `46e25ef261c9ea23cea45918f6059ab6f98c877c` (recorded before SS source edits). Existing retirement delivery documents and the user's edited REQ are preserved. AP/AR do not change source, run tests or mutate libraries.

## Decisions

- The user's edited scope is authoritative: discard every old studio `stories`/`jobs`/`progress` row; do not convert those rows into current stories or queue jobs. Protect every current `reader_sessions` row for every owner, including revisions, reselection records, unfinished work and recoverable deletions. A matching demo ID never overrides that protection. The final table is `stories`; keep API paths, module/type names, support-table names and existing `session_id` columns.
- Clear explicitly disposable book-reference records, not current story documents or protected media. Any underlying bytes used by current data survive. Keep current-story analytics events unchanged; delete only retired analytics and `published` deletion markers. Keep current deletion markers.
- Keep the historical SQL migration chain. Add one consolidation migration/upgrade step after it; new installations may run that chain and consolidation, as the edited REQ permits. Do not maintain a second fresh-install schema. Applied migrations are not rewritten. Remove old active ORM definitions and align the final Drizzle snapshot/journal so future generation cannot recreate retired tables.
- Record the first explicit library format as `PRAGMA user_version=1`; version 0 is accepted only with recognized historical shapes/migration records. Unknown or newer formats fail closed. Structural checks supplement the version: the old and new `stories` tables must never be confused. Reopening a completed library performs no conversion or backup. Pending recovery takes precedence over a seemingly final table/version.
- Target the first consolidated-schema-capable desktop and CLI release as **0.8.0**. Update their version declarations and release notes together; this is not permission to package or publish. Existing0.7.x binaries cannot be retrofitted with refusal checks and are documented as incompatible after consolidation. Rollback restores the pre-upgrade backup with its matching application version.

## Evidence and boundaries

`openDatabase()` currently runs each historical migration separately and seeds books afterward. `backupBeforeMigration()` already creates verified whole-library snapshots, but ordinary SQL rollback cannot undo filesystem deletion. `ownDesktopData()` holds `.desktop-owner.sqlite` inside the library for the lifetime of a Node service. Rust `library_summary`/deletion and the Vite preview bypass that ownership lock. Moving the entire library directory would move its lock inode and is not the upgrade design.

Desktop summary SQL joins `books`; keep the table and non-demo metadata. Runtime SQL also lives in `ReaderRepository`, production/intake/revision/reselection/command code, reference resolution, diagnostics and maintenance. Historical migrations and import source validation still need the original names at their explicit boundary. The CLI themes, providers, story schemas and rendering/export rules do not need redesign.

SQLite documents rename propagation into triggers/views and attached indexes; inspect the resulting schema and exercise its behavior rather than assuming source SQL was updated. Sources: [ALTER TABLE](https://www.sqlite.org/lang_altertable.html#alter_table_rename), [user_version](https://www.sqlite.org/pragma.html#pragma_user_version).

## Upgrade and recovery contract

Use one production upgrade coordinator, called before the production coordinator/workers start. Keep the library directory stable.

1. Inspect the database and any pending journal read-only for supported formats **before** creating ownership files, diagnostics, a backup or writable database connection. Recheck under the upgrade gate. A pending journal is not a fresh library even if `shiqu.sqlite` is temporarily absent; reject a journal from a newer unsupported upgrader without trying to recover it. A genuinely missing library keeps existing fresh-start semantics; missing-library desktop summary stays read-only and does not create a database.
2. Obtain service ownership for upgrade-capable operations and a distinct brief SQLite upgrade gate at a stable `.desktop-*` path. Native and preview database reads/writes participate in that same gate. They do not acquire the Node service's lifetime ownership lock for normal reads. No process can use the database during publication or rollback. Normal current-format operations remain lightweight.
3. Create and verify the existing whole-library safety backup, report its stable location, and durably record a pending-upgrade journal. This mandatory recovery snapshot is the only retained backup from this operation; there is no separate studio/demo archive. Upgrade runtime artifacts are excluded from backups. All source handles and SQLite WAL/SHM state must be accounted for before database replacement.
4. Stage a consistent database snapshot in the same library/filesystem and apply pending historical migrations and consolidation there, without starting generation. Plan purge candidates from the original studio rows before dropping them. Move only eligible files into reversible quarantine; never recursively delete a media directory. Keep the original database/WAL bundle recoverable and close all handles before publishing the staged database at `shiqu.sqlite`.
5. Under the gate, validate final schema, protected row/value equality and media hashes/reference integrity, complete eligible purge and remove temporary old database/quarantine artifacts, then record durable completion. Do not publish a ready service/library before this finishes. The verified safety backup remains outside the live library.
6. On any exception, or pending journal found after process death, restore the pre-upgrade database/schema and original file paths/bytes before allowing normal access. Use the original staged material or the verified backup if purge had begun. Recovery is idempotent; if recovery itself cannot finish, block normal access with the error and backup path rather than serving partial data. Logical database state and original media bytes must match the pre-upgrade inventory; SQLite checkpoint/layout bytes and transient lock files are not story content. A retry then performs the same upgrade. Close handles before replacement for Windows compatibility.

For a genuinely new library, build the historical chain and consolidation in an unpublished staged database through the same initializer, then publish the final schema. There is no original user library to back up; a failed first initialization leaves no partly initialized database available for use.

No whole-directory swap, live-provider work, unguarded post-commit file purge or permanent compatibility view is allowed. A runtime feasibility failure returns the plan to AR before dependent work proceeds.

## Purge policy

Inventory all protected rows directly, not through `repo.list()`, which hides revisions/deletions. Preserve the raw current story values and current job/command/fault/demand state. Inspect full selections/documents, revision bases and originals, current production job payloads/results/frozen image-input receipts, retained book-reference snapshots, saved originals and exports. Follow recognized local references through saved JSON artifacts; protect each current story's managed media namespace and preserve unknown/ambiguous ownership. Do not modify existing export artifacts. Retained current-use `/art/pear-N.png` and `/art/dongguo-N.png` URLs must still resolve through safe local media reads; bytes alone are not sufficient preservation. Do not serve an unreferenced retired asset just because an old file exists. Exclude the single safety backup and unrelated backups from purge traversal.

Candidates are only the REQ's known demo files/identities and local media positively referenced exclusively by retired rows/reference records. Shared and uncertain files are retained and reported. Remove unused reference snapshots only when ownership and lack of current use are established. Remove the specified `liaozhai` demo excerpt/source/note while retaining shared book metadata; remove `zhongshanlang` only when no protected current record uses that book, otherwise retain its metadata without demo text. Do not scan the bundled 24-book originals for matching literary passages or delete the legitimate original stories from that collection.

## Risks to resolve in implementation

Filesystem purge is not SQL-transactional; pending-journal recovery and access exclusion are mandatory. Native operations currently bypass Node ownership. A newer-format guard placed only in `openDatabase()` is too late for startup writes. Desktop book names still need shared metadata. Visible shelf membership is insufficient for cache/media ownership. Rename propagation must preserve durable trigger/receipt behavior. Corrupt or ambiguous protected data fails closed before purge, and a valid but ambiguous file remains retained.
